# TASK-006 — Candidate Authority & Concurrent Work State Foundation

Status: user-authorized foundation; implementation proposal recorded before code.
Basis: ADR-015/016, docs/CANDIDATE_AUTHORITY.md, docs/PARALLEL_EDITING.md.
TASK-005 / PR #6 approved and merged. Base main: fe8ee5e.

## Contract and scope

Build immutable state values and deterministic pure transitions. No actual candidate
timeline, duplication, editing, Apply, postflight, observer, persistence or UI exists.
Selection, approval, validity, application, verification, promotion and work phase
are separate axes, never a combined lifecycle enum.

## Proposed minimal domain

- CandidateId: explicit caller-supplied opaque fake ID. No random IDs/clocks/IO.
- CandidateBase: existing TimelineId + TimelineVersion (nonempty ID, nonnegative integer).
- CandidateLineage: immutable ancestor candidate IDs. Branch creates a NEW candidate ID,
  retains the root snapshot base and appends parent identity; no edits to the parent.
  No candidate registry/storage/duplicate-timeline implementation is implied.
- Candidate: ID, base, lineage, SelectionState, ApprovalState, CandidateValidity,
  ApplicationState, VerificationState, PromotionState, WorkPhase, optional ApplicationRecord.
- SelectionState: UNSELECTED / SELECTED; selection is per-candidate context only.
- ApprovalState: NOT_APPROVED / APPROVED. Only explicit ApproveCandidate event changes it.
  No natural-language praise interpretation, revoke or global approval coordinator.
- CandidateValidity: FRESH / STALE. Identity OR version mismatch makes it STALE.
  Once marked stale it cannot be made fresh by these transitions; no silent rebase.
- ApplicationState: NOT_APPLIED / APPLIED. VerificationState: NOT_VERIFIED / VERIFIED / FAILED.
- PromotionState: NOT_PROMOTED / PROMOTED. All verified/application history remains separate
  from current base validity. A promotion may make its old proposal base stale relative
  to the new authority; this does not erase historical application/verification facts.
- WorkPhase: ANALYZING / BUILDING_CANDIDATE / READY, descriptive only. No work scheduler,
  recomputation or commit loop. Changing phase never refreshes validity or grants approval.
- CandidateResultRef: opaque fake result ID + caller-supplied observed timeline/version.
  ApplicationRecord binds candidate ID, exact original base and result ref.
- WorkingAuthority: a fake comparison reference (CandidateBase) plus optional promoted
  result/candidate provenance. This is NOT the production WorkingAuthority storage schema.
- CandidateWorkState: one candidate, working authority and separate optional active timeline ID.
  Constructing/evaluating state with mismatching authority marks the proposal stale.
- CandidateTransitionResult: accepted/rejected, unchanged-or-new state, structured reason.
- ApplyEligibility: eligible boolean plus reason. Eligible means only candidate authority
  preconditions, never permission to bypass Safety Core or execute a timeline edit.

## Pure functions and evidence events

`branch_candidate(parent, new_id)` creates unselected/unapproved/unapplied/unverified/
unpromoted child from the SAME immutable source base. It preserves stale status, not
parent approval, applied result or authority. It does not mean branching from an applied
result; that representation remains OPEN. Duplicate/self/ancestor identity is rejected.

`transition(state, event)` handles explicit typed events:

| Event | Changes | Guard / non-effects |
| --- | --- | --- |
| SelectCandidate | selection only | never approval, active timeline or authority |
| ApproveCandidate | approval only | fresh, not already applied; explicit event, selection optional |
| SetWorkPhase | work phase only | descriptive, never clears stale or applies anything |
| ActivateTimeline | active timeline ID only | never changes authority or candidate base |
| ObserveHumanVersion | current authority version observation | same timeline only; backward observation rejected; mismatch invalidates candidate |
| RecordApplication | stores supplied application fact | eligible; exact candidate/base match; no Apply or version increment implemented |
| RecordVerification | stores supplied passed/failed fact | exact application record match; fresh; single verification result, no postflight execution |
| PromoteCandidate | explicit working authority + promotion provenance | approved + applied + verified + fresh; result observation must exactly match stored result |

Application/verification events are supplied simulation facts, NOT proofs generated by
this module. All evidence must be bound to the same candidate/base/result. The caller
must supply current source authority and result observations; this task cannot establish
their truth, detect live edits, lock state, or close TOCTOU races. This is an OPEN boundary,
not authorization to accept arbitrary production evidence. Invalid events fail closed
with a rejected result and no changes. Wrong value construction raises TypeError/ValueError.

An explicit observation of a newer human version updates knowledge of the SAME authority;
it never switches authority identity to a preview timeline. Only verified promotion may
switch the working target. No candidate base is rewritten, including after promotion.
Comparison checks identity and whole timeline version: no independent-region exemptions.
